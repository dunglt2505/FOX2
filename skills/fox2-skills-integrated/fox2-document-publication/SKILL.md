# fox2-document-publication

## Agile Lite project policy precedence

Policy v2.1.0 / `../shared/operating_rules.md` governs ordinary project work. Apply source publication, audit, immutable task and PreExec machinery only to actually selected governed release/Bridge/high-risk transport. For routine native DEV use one task, real deliverable and appropriate tests; preserve relevant professional checks, historical source locks, real permissions and no-replay.

## Activate when
Saving/syncing/publishing BRD, Policy, Technical Spec, Agent prompt or governed documents.

## Work to perform
Separate draft SAVE, Git push/readback, independently approved release and EFFECTIVE. Guard destination WIP and avoid overwriting byte-different sources. Read back exact bytes/hash after authorized save; release requires external trust chain.

## Completion / stop
Exact path, pre/post hash, commit, destination state and whether candidate/published/effective; never conflate stages.


Completion is governed by the **Execution Contract v0.3.6** below; apply conditional obligations only when triggered, report bounded HOLD otherwise.

## Execution Contract v0.3.6 — observable completion
- **TRIGGER:** Creating/saving/publishing approved Policy, BRD, TechSpec, task/prompt or audit report; includes authorized Git↔Library publication.
- **PRECONDITIONS:** Exact document type, Owner-approved scope, independently resolved source, destination rights and non-destructive WIP/writer checks.
- **REQUIRED_ACTIONS:** Publish only permitted artifact; verify Git bytes/commit; for governed docs complete required Library bytes/readback and current-pointer conditions; separate draft/candidate/published/effective.
- **REQUIRED_EVIDENCE:** Approved source version, actual pre/post SHA-256, Git commit/blob, destination/file evidence and Library readback where governing contract requires it.
- **DELIVERABLES:** Paths/hashes, publication receipt, destination comparison and precise status (`DRAFT`/`PUBLISHED`/`EFFECTIVE`/`HOLD`).
- **VALIDATION:** Compare actual source/destination bytes after write; check approval, release manifest/Registry effects independently; no silent overwrite.
- **FAILURE_STATE:** `PUBLICATION_HOLD` / `DESTINATION_CONFLICT` / `AUTHORITY_UNVERIFIED` for a required missing step.
- **COMPLETION_GATE:** Publication state evidenced at the correct layer; Git push alone is not document release, Library readback or EFFECTIVE.
## Git-first prompt publication
This Skill also applies when CHAT publishes Agent task, executable prompt and delivery instruction (not only Policy/BRD). For an executable handoff, write task + exact prompt to authorized non-main Git, verify full commit/blobs/SHA-256 and path scope, THEN assign Agent; a chat-only prompt is DRAFT. Publishing a prompt does not make PreExec, Agent result, acceptance or EFFECTIVE PASS. For Git ↔ Library documents verify exact destination bytes; keep distinct file publication, Owner-approved release and machine adoption statuses. No default WORK handoff for routine sync.

## Governance Release Lifecycle (R1, approval → publication → current pointer)
**Never confuse an Owner-approved human operating principle with machine release.** For a new Policy/BRD/TechSpec version, CHAT:
1. Establish the Owner approval (exact dated scope, predecessor, change class and external restrictions) and issue a bounded candidate/release record; an in-chat Owner directive may prove scoped *human* authority without inventing a cryptographic signature.
2. Publish the approved document to authorized non-main Git, verify immutable commit/path/blob SHA-1/SHA-256 and source/manifest identity. Git push alone is not an effective release.
3. Write the authorized Library destination without destructive overwrite, perform actual byte/hash readback (or explicit documented Owner-approved alternative). On failure: `PUBLICATION_HOLD`, keep Registry/Dictionary current unchanged and report real destination state.
4. Only after publication prerequisites and consumer compatibility are satisfied, update Dictionary/Registry *current* through its separately authorized source-change procedure; read back the new pointer, supersession, generator/normalizer bindings and affected tests. Never create a current pointer from filename ordering or self-declared EFFECTIVE.
5. Publish an exact status receipt distinguishing `OWNER_APPROVED_PRINCIPLE`, `PUBLISHED_EFFECTIVE` (only for the specifically verified scope), and `RUNTIME_ENFORCED` (only when installed runtime actually tested). Record missing machine attestation as `MACHINE_ADOPTION_PENDING`, not as a failed Owner decision or a fictional PASS.
Do not repeat Owner approval already evidenced within the exact scope. Owner exception to an *internal* sequence requires its own scoped/dated record with preserved FAIL/NOT_RUN; no invented readback, third-party rights, broker/LIVE or irreversible release.

## Complete publication without administrative pauses
An approved release request includes every authorized feasible stage: Git source publication/readback, required Library byte readback, consumer validation, permitted current-pointer update, exact scoped status receipt. CHAT must not stop after draft, Git push or a readback if later gates and permissions are already satisfied. On material failed gate keep release HOLD, do not promote current; finish all safe investigation/remediation within scope before reporting the real blocker. WORK is not routine publication executor.

## Prompt and audit report artifact publication (v0.3.5)
Authorized Agent handoff publication must retain exact Git task+prompt byte provenance and remote readback, whether recipient is WORK, CODEX or Copilot. WORK read-only source audit may still write named report/evidence files, not source code. If WORK cannot push, require actual exported file bytes (not prose) and CHAT-owned authorized Git publication with author/publisher separately attributed; remote readback before CHAT result acceptance. This Agent result/report publication does not make governed document `EFFECTIVE` and does not permit Registry pointer changes.
