# FOX2 — Agile Lite and Bridge execution compatibility (v0.4.1)

**Authority and scope.** Owner-approved FOX2 Policy v2.1.0, Routing v1.5.0 and Task/Result Protocol v13 govern NEW or properly re-scoped project management work. The actual selected Bridge runtime contract (its installed Dictionary, Schema v3, pinned preflight/adapter and ledger) controls a Bridge execution. These are different layers. Do not declare machine POLICY drift merely because an older immutable Bridge Dictionary names Policy 1.8.9; do not send Policy 2.1.0 to that Bridge's Schema v3 when its normalizer requires 1.8.9. A real machine migration requires a separately compatible consumer and tests, not mass-updated versions.

**No bureaucracy for native development.** CHAT chooses direct execution or CODEX/Copilot by residual task complexity and rights. Reversible independent native DEV: one task (goal, scope, actor, done_when, result); build, focused test, deliver. No default immutable Git prompt/Bridge Dispatch, formal R0–R7 worksheet, separate PreExec receipt, micro-WP, second review or extra approval.

**Bridge execution uses technical safeguards, not a new project-management lane.** For an actual Bridge-run task: select route and transport first; use the installed machine Dictionary/Schema; bind exact immutable task, prompt and source; verify only necessary scope and host conditions (one writer, clean owned worktree); acquire real material PreExec proof; create and validate a *new* Dispatch v3 that matches those proofs; publish it on the configured Git control branch and verify readback; Bridge transport polls, ledger claims one attempt, launches selected CLI, verifies output and publishes result; CHAT independently accepts or reworks the *same logical task*.

**Do not fake proof.** Source readback is not authorization. A Policy decision is not `decision_receipt=PASS` or `material_capability_check=PASS`. `NOT_RUN`, `UNKNOWN`, `BLOCKED` and `FAIL` remain what was observed. A draft Dispatch whose required PASS receipts are not observed MUST NOT be published to an executable control branch; do not publish an executable Bridge Dispatch without real proof. This is the no-replay boundary. Do not invent installed CLI version/flags, worktree, hashes, model or executable. Do not change branch ownership, retry consumed/claimed Dispatch, reset unrelated WIP, merge main, deploy, broker-write or perform LIVE activity merely because a skill requests it.

**Source hygiene.** Historical Policy/Dictionary references and consumed Dispatch locks stay unchanged; fix the one active resolver or incompatible consumer proven wrong. Keep agreed task boundaries and reuse valid PASS. Status labels: `SOURCE_DRAFT`, `HANDOFF_SOURCE_VERIFIED`, `DISPATCH_ADMITTED`, `AGENT_STARTED`, `PUSHED_UNREVIEWED`, `CHAT_ACCEPTED`/`REWORK`/`BLOCKED`; every label requires its corresponding observed evidence, not a text claim.
